Pre-modelling review — technical guide

Updated 12 October 2026 · Sam

The review checks the raw SAS extract, fixes structural gaps, proposes the light-touch levels Radar applies before Emblem, shows an indicative Emblem grouping for each peril, and screens factors with feature importance and correlation. This guide explains every calculation behind it and how the pieces connect.

How it fits together↑

Steps 1–6 run in Python in one go. The checks propose fixes that you confirm in CONFIG before the next run, and only the reports and the Radar spec leave Python: Radar applies the rules and writes the Emblem data, and Emblem makes the final modelling decisions.

Five files work together; run_review.py is the only one you edit or run, and it calls the other four.

Loading and preparing the data↑

The run reads only the columns it needs, cleans the claims fields, and records every change in the report's Data checks list.

load_data(path, columns) reads .sas7bdat, .xpt, .csv or .parquet.

  • Columns read: every factor in FACTORS, exposure, policy year (if PERIOD is set), product, the section cover flags, and one count and one cost column per peril (built from COUNT_COL and COST_COL, e.g. No_Of_Claims_AD).

  • Names are matched ignoring case, because SAS often stores them in capitals. Each column is renamed to the spelling in the config, so everything downstream uses your names.

  • With pyreadstat installed, it reads the file's metadata first and then only the requested columns. Without it, pandas reads the whole file (as latin-1 text) and the rest are dropped.

  • A requested column that isn't in the file stops the run with a list of the names that are there.

prepare(df, exposure, counts, costs) applies four fixes, in this order:

  1. Blank claim counts and costs become 0. A blank means the policy had no claims of that peril. With more than two such columns, the report gives one summary line.

  2. Rows with zero, negative or blank exposure are removed. They can't contribute to a rate.

  3. Negative claim costs (net recoveries) are set to 0, because a Tweedie model can't take a negative response. The note gives the number of rows and the total removed.

  4. Rows with a cost above 0 but a count of 0 are flagged, not changed. These are usually reopened claims or IBNR allocations.

Categorical clean-up. SAS stores numeric codes as decimals, so a trade code of 101 arrives as 101.0. For factors in CATEGORICAL that hold whole numbers, the values become text ("101"). Other text values have spaces trimmed. Product is trimmed too.

All-perils totals. After engineering, two working columns are added: total claims (_n_all) and total cost (_c_all) across all perils. They drive the all-perils report, including its importance model.

Feature engineering↑

engineer(df, cfg) applies only the fixes you have confirmed in the config, on a copy of the data, and logs each one under its factor in the report. Nothing is changed on a proposal alone.

The steps run in this order, so later steps see earlier results:

  1. Mappings (MAPPINGS). Raw values are replaced by harmonised ones, from a dictionary or a two-column CSV (raw, mapped). Values with no mapping are kept as they were, and the count is logged.

  2. Placeholder text. In every text factor, values in STRING_PLACEHOLDERS (blank, UNKNOWN, N/A, NULL, TBC and so on, ignoring case and spaces) become missing. The values actually found are recorded for the Radar rules.

  3. Junk rules (JUNK). Infinite values in numeric factors (a ratio divided by zero) become missing first, with a line in the log. Then listed placeholder values (values) and anything outside a valid range (below, above) become missing.

  4. Not applicable (APPLIES_TO). Rows where the factor doesn't apply get the N/A code. A rule can name products ({"products": ["CPO", "RE"]}), a section ({"section": "Buildings"}), or both.

What counts as applicable. A product rule applies only to the listed products, so blank or unexpected products count as not applicable. A section rule applies only where that cover flag is Y (ignoring case and spaces); N or blank counts as not applicable.

The N/A code. Text factors get the value "N/A". Numeric factors get a reserved number:

  • −1 when every real value is 0 or above;

  • otherwise one below the lowest real value, rounded down;

  • or the number you set with "reserved" in the rule.

If the chosen code already occurs in the real data, the run stops rather than mixing the two. Any real values sitting in not-applicable rows (often zeros) are overwritten, and the log says how many.

Junk in Python and in Radar. In Python, junk simply becomes missing. Radar's formula language can't create an empty value, so the spec gives numeric junk its own code instead: one below the N/A code, or −1 when the factor has no N/A. Radar's Banding rules then send that code to Unknown, alongside NoValue. Text placeholders are sent to Unknown by = rules. Both routes end at the same level.

detect_structural looks for missing values (and, for numeric factors, zeros) that sit almost entirely in some products or where a cover section is N. It only runs when at least 1% of exposure is missing (or zero), and not for factors already in APPLIES_TO.

  • By product. For each product, missing rate = missing exposure ÷ that product's exposure. Products at 95% or more are "absent"; products at 20% or less are "present". It proposes a product rule only if every product falls into one of the two groups and the absent products hold at least 80% of all the missing exposure.

  • By section. For each cover flag, it compares the missing rate where the flag is N (95% or more) with where it is Y (20% or less). N rows must hold at least 80% of the missing exposure.

  • When both fit, the explanation covering the larger share of the missing exposure wins. The proposal is "applies to" the present products, or to the section being Y.

The figures at the top of each factor's section are: Missing (raw), the share of all exposure missing before any fixes; N/A, the share of all exposure coded N/A; and Unknown, the share of applicable exposure still missing after the fixes.

Product, section and peril cover checks↑

These three tables open the all-perils report (switched by data_checks and cover_check). They describe the book rather than any one factor.

product_summary gives, for each product: rows, exposure, share of exposure, claims for each peril, and burning cost (total cost of all perils ÷ exposure). Products are listed in the order of PRODUCTS, then any unexpected values, including blanks. Unexpected products are named under the table, because Radar's product rules will send them to UNKNOWN. A second table shows exposure by policy year and product.

section_mix shows how each product's exposure splits across the cover combinations, e.g. Buildings Y / Contents N. Each column is one product and sums to 100%.

cover_check looks for perils that a product or cover combination probably doesn't include.

  1. The data is split by product × each section flag. Combinations with less than 0.5% of exposure are left out.

  2. For each peril, expected claims = the combination's exposure × the peril's overall frequency (all claims ÷ all exposure).

  3. The table shows actual ÷ expected, shaded darker for higher values.

  4. A combination is flagged "possibly not covered" when at least 10 claims were expected but 10% or fewer of them happened.

Nothing is excluded on the strength of this check. It's there so that, for example, AD showing zero claims outside RE is noticed and raised with underwriting.

The three views↑

Each factor is shown at three levels of detail. Each view starts from the one before, and all three use the engineered data. The first two group nothing unless they have to, so no information is lost before Emblem.

All three are built only on rows where the factor applies and has a value. N/A and Unknown are added as their own levels at the end and are never merged into anything. Spikes (below) are never merged in any view.

Spikes — find_points

A spike is a single value holding a lot of exposure compared with its neighbours: 0 years trading, or a default sum insured or turnover. It is its own kind of risk, so it is always its own level, whatever its claims.

  • A value is a spike when it holds at least 2% of applicable exposure (point_min) and at least 3 times (point_ratio) the average share of up to two neighbouring values on each side. An even spread (60 values with about 1.7% each) has none.

  • Its band runs from the value to the next whole number (whole-number factors) or to the shortest round number above it and at or below the next value (decimals: a spike at 0 with the next value 0.01695 ends at 0.01), so it holds that value alone and is named by it ("0", "100,000").

  • The edges either side of a spike are protected: no merge ever removes them (protected_edges).

  • For factors with over 20 distinct values, each spike is listed in the data checks as a Check: kept as its own level, but worth confirming it isn't a default or rounded input. The check and the levels use the same rule (find_points), so they always agree.

1. Raw data — raw_spec

  • Numeric, up to 1,000 distinct values (raw_max_levels): one level per value, including values with no claims.

  • Numeric, more than 1,000 distinct values: about 250 equal-exposure bins (raw_bins). The cut points are the weighted quantiles at 1/250, 2/250…, each rounded to three significant figures (41,372 → 41,400), with duplicates dropped and spike edges added. This is the only case where the raw view bins at all; sum insured and turnover are the usual examples.

  • Categorical: every level, ungrouped, largest exposure first. Only beyond 1,000 levels (raw_max_cat_levels) are the smallest shown together as "(other levels)".

Weighted quantiles (_weighted_quantiles) weight each value by its exposure. Values are sorted; each sits at the midpoint of its share of cumulative exposure; the quantile is read off by straight-line interpolation between them.

2. Suggested levels — tidy_spec

This is a light-touch tidy-up, not grouping. Emblem allows 255 levels per factor, so the suggestion stays as close to the raw data as that limit allows and leaves all real grouping to Emblem. It uses all perils together, so one set of levels serves every peril model.

For a numeric factor:

  1. Up to 250 distinct values (max_levels): one level per value, nothing grouped. The top level is open ("59+") so a future higher value still lands somewhere. Radar's Generate › Unique option can build these rules for whole numbers. For decimals (a ratio such as claims per property), each cut point is the shortest round number between two neighbouring values (between 0.1429 and 0.1667 it's 0.16), so the rules still put every value in its own level after the bounds are pasted into Radar; a long repeating decimal such as 0.6666666666666666 can round up on the way and push a value into the level below.

  2. More than 250 distinct values: about 200 equal-exposure bins, sharing out the exposure left after any spikes (tidy_bins), each cut point rounded to two significant figures (41,372 → 41,000) so the bands read as round numbers, duplicates dropped.

  3. Far tails (binned factors only): the weighted 0.1th and 99.9th percentiles (tail), rounded the same way, become the floor and the cap. Cut points beyond them are dropped; the cap starts the open top band ("4,500,000+").

  4. Spikes get a band of their own, as above.

  5. Empty bins merged (merge_adjacent): a band with no exposure joins its neighbour with less exposure. Nothing else is merged. If more than 250 bands were left, the band with the fewest claims would join its smaller neighbour until 250 remain.

For a categorical factor, every level is kept. Only when there are more than 250 levels do the smallest by exposure go to OTHER, so the factor fits Emblem's limit with room for Unknown, N/A and OTHER. If the data already has a level called OTHER, grouped levels join it rather than creating a second one. A minimum exposure share (min_expo, default 0) can also send tiny levels to OTHER.

When grouped levels leave OTHER with 20% or more of exposure, the report raises an Action: a parent grouping through MAPPINGS (trade code to trade group, say) keeps more detail than one large OTHER.

An entry in TIDY_OVERRIDES replaces the suggestion completely: your cut points (edges) or kept levels (levels) are used as given, with no merging. For factors with 60 levels or fewer, the report prints a ready-made line to edit.

3. Indicative Emblem grouping — group_spec

This starts from the suggested levels and merges them until each group has enough claims for the peril in question. It's run separately for every peril and for all perils combined. It's a one-way guide only: Emblem's grouping, after fitting the other factors, decides.

For a numeric factor (merge_adjacent, working on each band's exposure, claims and cost):

  1. Find the band with the fewest claims for this peril (on a tie, the one with less exposure).

  2. Stop if every band has at least the peril's minimum (MIN_CLAIMS_GROUP: 100 by default, 200 for all perils, 50 for Fire and Storm, 25 for Flood) and there are no more than MAX_GROUPS (15).

  3. Otherwise merge it with a neighbour. An end band has only one. A middle band joins the neighbour whose burning cost is closer, compared on a log scale, so a genuine step in the curve survives. On a tie, or when a burning cost can't be worked out, it joins the neighbour with fewer claims. A spike's edges are never removed, so a spike stays a group of its own; when both of a band's edges are protected, the next thinnest band is tried instead.

  4. Repeat from step 1.

For a categorical factor, a suggested level keeps its own group if it has at least the peril's minimum claims or holds at least 2% of exposure (point_min), so a large level is never lost in OTHER; the rest join OTHER. When OTHER ends up with half the exposure or more, the report says so: no level is big enough to stand alone for that peril, and Emblem will need a parent grouping or levels grouped by similar relativity.

Level names — band_names, numeric_labels

Bands include their lower edge and exclude their upper edge, so cut points at 25 and 30 give <25, 25–29, 30+. For whole numbers the label shows the last value inside the band; a one-value band shows just that value; the lowest band starts at the data's minimum ("0" or "0–1" rather than <2). For decimals the labels read <a, a<=x<b, >=b. A one-level-per-value factor is named by its values, the last with a "+", and a spike's band by its value. Numbers carry thousands separators, except for years (whole numbers with 99% of exposure between 1800 and 2100, detected by year_like) and factors listed in NO_COMMAS, so 2026 rather than 2,026. They never use scientific notation, and no two levels share a name.

Relativities, base level and scaling↑

Every relativity is a one-way ratio of a level's experience to the whole book's, then rescaled so the base level reads 1.00. In a peril's report the claims and cost are that peril's; in the all-perils report they are the totals.

Raw relativities (level_table). For a level L, with exposure E_L, claim count N_L and claim cost C_L, and book totals E, N and C over every row (N/A and Unknown included):

frequencyL=NL/ELN/EseverityL=CL/NLC/Nburning costL=CL/ELC/E

The per-product lines (switched on from the legend) use the same burning cost formula on one product's rows within the level, still divided by the whole book's C / E. Burning cost relativity equals frequency × severity relativity.

Rescaling to the base (rescale). Each relativity is divided by the base group's value for the same measure, so the base reads exactly 1.00 for burning cost, frequency and severity alike:

relativityLshown=relativityLrelativitybase

All three charts for a factor in one report use the same divisor, so 1.3 means the same thing on each. Ratios between levels don't change.

Choosing the base (factor_views, pick_base_level):

  1. If BASE_LEVELS names one of the factor's suggested levels, that level is the Radar base level. The base group is the indicative group containing it.

  2. If it names an indicative group, that group is the base group.

  3. Otherwise the base group is the indicative group with the most exposure, leaving out N/A, Unknown, OTHER and "(other levels)", and any group with no claims.

  4. When the base group came from step 2 or 3, the Radar base level is the suggested level with the most exposure inside it.

  5. A name in BASE_LEVELS that doesn't exist falls back to step 3, and the note says so. With no usable group at all, relativities stay relative to the average.

The base can differ between reports, because the indicative groups differ by peril. The Radar base on the spec's Levels sheet comes from the all-perils report.

Relativity spread = the highest ÷ the lowest burning cost relativity among the indicative groups that meet the peril's minimum claims, leaving out N/A and Unknown (OTHER counts). It needs at least two such groups. Being a ratio, it doesn't depend on the base. It's a rough one-way guide to how much a factor moves: correlated factors share one effect between them, so a high spread isn't proof of a real effect, and a low one isn't proof of none.

Stability by year (the collapsed block under each factor). For each policy year, every indicative group's burning cost rate is divided by that year's overall rate, then by that year's base-group value, so each year's base reads 1.00. One line per year, light (oldest) to dark (newest). Lines that roughly overlay mean the pattern holds over time; a group that flips between years is noise or a change in the book.

What to look for. The stacked bars show where each product's business sits. A level made almost entirely of one product can't be separated from that product's effect. Burning cost moving with frequency points to more claims; moving with severity points to bigger claims. Product lines that run parallel mean the factor behaves the same in each product; lines that cross or diverge point to a product interaction worth testing in Emblem.

Each factor section also has a table under the suggested levels and under the indicative grouping (closed by default; the tables switch). It lists exposure, exposure share, claims and the three relativities, with thin levels highlighted and the base marked "(base)".

Feature importance and correlation↑

Both are screens for choosing which factors to take into Emblem, not models. Importance appears in every report; correlation in the all-perils report only. Both sit above the factor sections.

Feature importance (gbm_importance). A gradient boosting model of burning cost (claim cost ÷ exposure, weighted by exposure) is fitted with every factor at once, plus product and the cover flags as context. It uses LightGBM with a Tweedie objective (power 1.5), or scikit-learn's HistGradientBoostingRegressor with a Poisson loss when LightGBM isn't installed. It's fitted separately for every peril and for all perils combined.

  1. Inputs. Numeric factors go in as their engineered values (N/A as its code, Unknown as missing, which the trees handle); categorical factors as their suggested levels; product and the cover flags as categories. A column of random numbers, _noise_, is added as a benchmark. Above max_rows (500,000) a random sample is used.

  2. Cross-validation. Rows are split at random into 5 folds (folds). Each fold is held out once and predicted by a model trained on the other four.

  3. Over-fitting controls. Each model sets aside 15% of its training rows and stops adding trees once 30 in a row (early_stop) fail to improve the deviance on them, up to 1,000 (max_trees), at a learning rate of 0.05 with 15 leaves per tree. A leaf needs enough rows for about 10 claims on average (min_claims_leaf): 10 × training rows ÷ training claims, at least 50 and at most a twentieth of the rows. Categorical splits are smoothed so a level with few rows can't drive a split.

  4. Shuffle each factor. In the held-out fold, one factor's values are shuffled across rows, which breaks its link with the claims but keeps its distribution, and the model predicts again (twice, perms, averaged). A factor with an N/A level is shuffled only among the rows where it applies, so its score is what it adds beyond the product / section split, which Emblem carries with the N/A level fixed at 0.

  5. Score. Importance is the deviance lost, pooled over the folds, as a percentage of the deviance of a prediction that is just the training average. D_k is the exposure-weighted Tweedie deviance (power 1.5) on held-out fold k:

importancef=100×∑kDk(model,f shuffled)−∑kDk(model)∑kDk(average only)

The whiskers on the chart show the same calculation fold by fold, lowest to highest. The note above the chart gives the model's explained deviance: the same ratio for the model against the average-only prediction.

  • Noise benchmark. A factor is "no better than noise" when its importance is at or below the noise column's highest fold score (or 0). Its bar is grey, and the factor tables show "(noise)" after its rank.

  • % of the top factor. Each factor's importance divided by the top candidate factor's, context flags left out. This is the Importance column in the factor tables and the value in each cell of the all-perils report's "Importance by peril" table, where a faded cell with a dot is no better than noise for that peril.

  • Context flags (product, cover) are light blue. When one far outscores every factor, such as product for a peril only one product covers, its bar is cut at the edge of the axis and labelled with its value.

  • Warnings. Under 300 claims (min_claims_warn) the report says importances are rough. When the model predicts held-out data no better than the average, it says any factor above the noise line is weak evidence.

Reading it. Importance allows for the other factors, unlike the one-way relativity spread, so a factor that only looks strong because it moves with another scores lower. Two correlated factors share the credit, though: each can stand in for the other when one is shuffled, so both can look weaker than they are. Read it with the correlation section's linked pairs and groups.

Correlation (cramers_v_weighted, correlation_matrix). Cramér's V for every pair of factors, plus product and the cover flags. Numeric factors use their indicative groups for all perils (at most 15 plus N/A and Unknown); categorical factors use their suggested levels. N/A and Unknown count as levels. The cross-table is built from exposure, then scaled to the row count n so the usual chi-square applies. With r and k levels, the bias-corrected V (Bergsma) is:

φ~2=max(0, χ2n−(k−1)(r−1)n−1),r~=r−(r−1)2n−1,k~=k−(k−1)2n−1,V=φ~2min(k~−1, r~−1)

V runs from 0 (unrelated) to 1 (one factor determines the other). The section is built to stay readable with a long factor list:

  1. Linked pairs: every pair of factors with V of 0.3 or more (CORRELATION["flag"]), strongest first, marked Strong from 0.7 ("strong": likely to alias or be unstable together in Emblem) or Moderate. Each factor's all-perils importance sits beside it, because where two factors overlap the more important one usually carries the effect.

  2. Groups of linked factors (correlation_clusters): factors joined by those pairs, directly or through each other (A–B and B–C put A, B and C in one group), most important first. Each group is a set to look at together.

  3. Links with product and the cover flags, collapsed. A factor with an N/A level always shows one; that's expected, and handled by fixing the N/A level.

  4. Full matrix, collapsed, only when there are at most 20 factors (heatmap_max). Every pair is also written to correlation_<VERSION>.csv, to sort or filter in Excel.

Each factor's levels are coded once and every pair's table is built in a single pass, so a long factor list stays quick.

Categorical factors with more than 50 raw levels also get a CSV, tidy_map_<factor>_<version>.csv (raw, level), to join in Radar rather than type hundreds of rules.

Formulas (radar_formula). Each engineered factor gets a new variable, <Factor>Model, which is what you band. The N/A test comes first; the junk test is nested inside it:

YearsTradingModel = If Product <> "CPO" And Product <> "RE" then -1 else (If YearsTrading = 999 then -2 else YearsTrading);
EmployeesModel = If Employees = 9999 then -1 else Employees;

A product rule becomes "product is none of the listed ones", so blank and unexpected products are N/A too. A section rule becomes <flag> <> "Y". Variable names come from RADAR_NAMES where set, because Radar names can't contain spaces.

Banding rules (banding_rules) are built so no two rules can match the same value; the order you enter them doesn't matter. For a numeric factor (years trading: one level per value, N/A code −1, junk code −2):

The lowest band is two-sided, starting just above the highest reserved code, so the codes never fall into it. Without reserved codes it is simply "< first cut point". The top band is open. A spike gets a two-sided rule of its own (>= 100000 and < 100001 → "100,000"). For a categorical factor there is one = rule per raw value, mapping it to its level or OTHER, plus = "N/A", an = rule for each placeholder text found, and NoValue, the last two going to Unknown. The rules type is Float or String, following the column's type in the source data: a categorical stored as numbers (trade code 101) gets Float rules with numeric values, and a numeric N/A code (−1) in its formula, because that's how Radar reads it. A categorical's JUNK values each get an = rule to Unknown.

Levels. Level names are listed in the order to enter them: bands (or levels, then OTHER), Unknown, N/A. Tick Ordered for numeric factors. "Base level" marks the Radar base (see Choosing the base). "Variate x" is each band's exposure-weighted average real value (variate_x), the x-value to give that level if you fit a curve in Emblem. "Note" on a factor's first row says "one level per value" (Radar's Generate › Unique can build those rules instead of typing them) or "every level" (a categorical factor kept whole).

In Emblem:

  • Fix the N/A parameter at 0 (relativity 1.00) with Fixing Factors. Product or section relativities then carry those policies, and the factor only adjusts the policies it applies to.

  • The base levels set in Radar's Banding component carry into the Emblem file.

  • For each peril, have Radar write a claim-count file alongside the burning cost file, in the same row order, so the Tweedie tool can estimate the variance power accurately.

  • Final grouping is Emblem's: the indicative grouping is a starting point, not a decision.

Testing changes↑

A test pack checks the whole review in about a minute, so any change to the scripts can be checked before it's used. Put the tests folder next to the scripts and run python tests/run_tests.py (or %run tests/run_tests.py).

  • Test data (make_test_data.py): 60,000 synthetic rows, made on the first run with a fixed seed, holding every awkward case so far. Those include structural N/A by product and section, spikes at 0 years trading, a 100,000 turnover default and a 1900 build year, junk codes, trade codes stored as numbers (380 of them), placeholder text, an OTHER already in the data, years, and two ratios (one binned, one with a level per value, with division by zero).

  • Checks (run_tests.py, 46 of them): config typos stop the run; Radar's rules, applied to the source data as Radar would, give exactly the Python levels on every row for every factor; every value lands in its own level; decimal cut points survive Radar keeping only 6 significant digits; spikes are kept; OTHER isn't duplicated; years have no commas; trade code gets number rules; small Unknown is flagged; filter, split and empty factors work.

  • Baseline: --save-baseline stores the spec sheets, the correlation table and every factor's indicative groups for every peril. Later runs compare against it and list the first lines that changed. Save a baseline on your machine first; after a change, a difference is either intended (save a new baseline) or a side effect to look into.

The tests use their own fixed settings and write to tests/output, so they never touch your CONFIG or your real outputs. Each kind of bug they target was introduced on purpose (eight of them) and every one was caught.

Assumptions and limits↑

The charts and the grouping are one-way and rule-based, and the importance model is a screen. Together they prepare the data for Emblem but don't replace Emblem's multivariate judgement.

  • One-way charts. Relativities, spreads and the indicative grouping ignore other factors. A factor correlated with another (sum insured with turnover, say) can look stronger or weaker than it will in Emblem. The importance model and the correlation heatmap are there to catch this.

  • Importance shares credit between correlated factors, and with few claims it is noisy. Trust a factor that clears the noise benchmark with its whole whisker, not by a small gap. It ranks factors; it doesn't say how to band them or whether an effect will hold in the multivariate model.

  • Thresholds are sensible defaults, not calibrated. The spike test (2% of exposure, 3× the neighbours), the 95% / 20% / 80% structural tests and the per-peril minimum claims were chosen to suit a typical SME book. Thin perils such as Flood may need different values.

  • Exposure is not adjusted for cover. The cover check flags combinations that look uncovered, but those policies still count in that peril's exposure.

  • Claims are used as supplied. Large-loss capping isn't applied. Claims arrive summed per policy, so any capping per claim has to happen before the extract.

  • Values below the reserved codes (e.g. a negative value in a field coded −1 for N/A) would match no Radar rule. Add a junk range in JUNK if that can happen.

  • New categories after a refresh match no Radar rule, because the categorical rules list every value seen. Numeric rules are ranges, so new numeric values always land in a level. Check for unbanded values after each refresh.

  • Tested on made-up data so far. Reading a real .sas7bdat file (the tests used .xpt), pasting rule rows into Radar's grid, the formula syntax in your Radar version (written from the Radar 4.3 guide), and the importance run time on the full book are still to confirm.

  • Not built yet: a holdout flag, and product × factor actual-versus-expected checks after fitting.
